# Renderer ownership contract

S-073 implements the owner's approved twelve-step renderer refactor. This is a behavior-preserving change to the existing React application, not a new UI framework, persistence model or payment workflow. The baseline is `2e2b8417d42714656991066bb4909ee65058b6d0`; executed checks and final paths belong in the [story handoff](../progress/handoffs/S-073.md). The twelve steps are reviewable commits within this authorized story, not permission to start later product stories.

## Boundary and dependency rules

`src/App.js` is the composition boundary: assemble owners, supply their explicit dependencies and select the active screen. It must not own feature workflows, feature view-model construction, feature dialogs, request-token maps or a copy of every feature's state. A smaller App achieved by renaming the old class to a workspace, facade or controller does not meet this contract.

Each feature owns its state, effects, busy/error states, request identity, cleanup, view model and controls. Read-only snapshots and named commands cross boundaries. A command names an operation such as `openTable(tableId)`, `applyConfirmedItems(orderId, items)`, `completeHandoff(notice)` or `retryJob(jobId)`; it must not expose arbitrary writes. Exact filenames and method spelling may follow local conventions, but the ownership and lifetimes below are mandatory.

- Do not pass the App instance, the whole application state, `setState`, `mut`, an unrestricted dispatcher or callbacks that edit another owner's internals into a feature. Do not recreate these access paths through a service locator, proxy, prototype mixin or shared all-feature state bag.
- A component receives its own view model and named actions, not the former all-screen `renderVals()` object. Use feature-local presentation helpers; shared formatting/style/translation helpers remain pure.
- Keep one authoritative renderer copy of each table, order and item. Features may hold a draft or immutable response snapshot for their workflow, but commit confirmed results through the data owner's domain commands. The desktop service remains authoritative for permission, money, persistence and retries.
- Sharing a mutation gate for the selected order is intentional. The order-data owner coordinates item edits, send, move and correction; each feature still owns its request payload and outcome. Publish only the activity/lock information needed for navigation and controls. Do not allow two feature-local busy flags to admit concurrent writes formerly excluded by `_itemBusy`.
- Compose ordinary modules with explicit imports and the existing esbuild build. React/ReactDOM may remain the bundled vendor runtime; application features must not depend on script order, `ArraComponents`, `render*.call(this, ...)`, implicit global helpers or browser-only globals to load in tests. Do not introduce a state-management framework or general event bus.
- Capture desktop/demo mode and the bridge once at startup. A missing or disconnected desktop bridge never activates sample data or simulated mutations. Only the explicitly selected demo entry may start without a bridge.

## Cross-feature transitions

1. Session selection clears protected data, then asks the catalog/table owners to load for the new identity. Responses carry their owner generation and cannot repopulate an old identity's data. Independent print retry identity is retained; clearing protected data must not erase a committed-but-unacknowledged retry.
2. Pending items, send, movement and correction use the same order-write exclusion. Owners publish confirmed data through explicit order commands. Root merely wires the required callbacks; it must not interpret their results or contain their fallback branches.
3. Confirmed send updates items, asks printing for current status and composes pending/uncertain/physical-print notices before requesting session handoff. Keep the guard during the entire chain, including a slow print-status request and a failed identity clear.
4. Confirmed payment signals the session handoff once. Billing owns uncertainty and selections; App does not reconstruct payment data or retries. Demo completion additionally asks its data/printing owners to retire the completed table's working data.
5. Movement and correction reconcile against stable order identity. Generic `onChange(patch)` or `mut(fn)` callbacks between features are not substitutes for these commands. Derived display values must not become another mutable source of truth.

## Permanent enforcement

The final renderer uses explicit bundled imports. App composes feature owners, subscriptions, lifecycle and routes; it contains no feature state, aggregate renderVals, generic mutation helper or workflow handler. Shell owns clock/toast presentation; catalog, order data, pending editing, sending, movement, correction, printing, session/settings, administration and billing retain the responsibilities and lifetimes above. Demo billing/history and printing use separate owners and named order-data commands. Order layout receives separate catalog, pending, order, send, move and bill projections, not an all-screen object.

Both test and build execute the architecture gate; npm run check:architecture runs it alone. scripts/renderer-architecture.json records the reviewed normalized App source and permitted layer dependencies. There are no migration exceptions. The check rejects new App behavior (including code inserted into existing methods), privileged renderer imports, reverse/forbidden feature dependencies, unknown layers and cycles. Negative tests exercise each boundary. Formatting/comments alone do not require changing the App contract.

An intentional composition or dependency change requires explicit architectural review of the actual source diff and contract together. Never regenerate the contract merely to silence a failure or admit new feature logic. The gate does not prove semantic ownership: review must also reject whole-app props, generic mutation injection and replacement monoliths. These are local gates; no CI enforcement is assumed.
