# Safe upgrades and rollback (sample development)

This is a manual rehearsal procedure, not approval for live sales. S-032 still requires a separately protected copy and recovery on another machine; S-036 covers release readiness. The current sample release uses Electron 45.2.1, Node 24.22.1 and its bundled SQLite. Rehearse the exact release and data version before installing a future release; these checks do not prove future migrations or hardware failures safe.

1. Identify the actual data directory and installed version. Stop all Arra POS instances and any other process writing that database. Keep them stopped until the snapshot is complete. Check free space for the database, temporary snapshot and encrypted backup, as well as the upgrade. Follow [backup and recovery](backup-recovery.md) to create a new encrypted backup outside the data directory. Do not install or open the new version if backup fails.
2. Restore that backup into a new empty, restricted directory and verify integrity and known sample orders, payments, corrections and users using the old compatible version. Preserve the encrypted backup; do not use the verification copy as the only backup. With sample data only, rehearse the new release against a separate fresh restore and verify the same records, restart and ordinary workflows. The new release may modify that copy.
3. Retain the old installer and backup. With the app stopped, install the new release and launch it against the intended data. Check startup and representative data before resuming work. A startup error can indicate insufficient disk space, permissions, an incompatible newer database or another failure; preserve the database and SQLite sidecars, investigate, and do not repeatedly retry until the cause is understood. Do not delete a journal or WAL to make startup work.
4. If rollback is necessary, stop the application. Preserve the entire post-upgrade data directory and its sidecars separately for investigation, including any records made since upgrade. Restore the pre-upgrade encrypted backup into a new empty restricted directory and verify it with the old compatible release before arranging for that release to use it. Do not point the older release at an upgraded database, overwrite the original in place, or manually combine histories. A pre-upgrade restore excludes all subsequent activity; reconcile that activity by an authorized, separately planned process before resuming. A successful migration is not reversible merely by reinstalling old code.

The migration transaction rolls back failed or interrupted migrations under SQLite's recovery guarantees, but this does not replace a verified backup or protect against hardware failure, corruption, or lost writes. Keep the old version and backup until the upgrade and recovery have been verified. The tested v33 fixture and injected failures are a development rehearsal, not a physical power-loss or actual full-disk test.
